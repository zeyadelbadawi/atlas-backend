## 1. Executive Summary

**Answer:** yes, conditionally. The existing Atlas can become the commercial production platform with a **bounded** set of changes. The identity, RBAC, RLS, dashboard, Academy, onboarding, billing and communications internals stay.

The work adds four things:
1. **A host context layer.** One registry of Atlas labels shared by Organizations and Academies, a host resolver in the backend and the SPA, and new routing modes in `AppRouter`.
2. **Context-bound authentication.** Every session, OTP challenge, trusted device and reset token is bound to `platform`, `organization:<id>` or `academy:<id>`. The context is **fixed at minting and signed into tokens**, while roles are never put in tokens. The **existing guards** then add one equality check.
3. **An organization-level OTP policy**, owned by the Client Owner.
4. **Launch hardening:** the three security defects already found (D1–D3), the plan v2 onboarding fixes, CSP, RLS tightening, a controlled **test-data reset**, and a production launch gate.

**Launch blockers** that must be closed before commercial launch (§36):
- **LB-DOMAIN**: production lives on a free third-party domain.
- **D1**: an academy token is a management credential.
- **D2**: staff-chosen passwords on other people's accounts.
- **D3**: password reset leaves access tokens alive.
- **LB-PAY**: no payment method is configured.
- **LB-EMAIL** (KI-EMAIL-1): must be re-measured, because OTP, reset and invites all depend on email.
- **LB-HOST**: forwarded-host trust must be verified.
- **LB-RESERVED**: infrastructure labels (`video`, `ssh`) are missing from the reserved list.

- **Authentication:** see plan v2 §2. JWT `{sub,sid}`, 15 minutes. Rotating refresh token with `surface` (`management`/`academy`) and `academy_id`. Per-origin `localStorage`.
- **Authorization:**
  - `JwtAuthGuard` → `ManagementSurfaceGuard` (refuses learner principals).
  - Tenant guards that re-derive the organization from the database per request: `OrganizationMembershipGuard` (org id in path), `AcademyScopeGuard` (academy id in path → org), `AcademyOrganizationScopeGuard` (org id in query or body).
  - `PlatformOwnerGuard`.
  - RLS.
- **Controller inventory** (the `ManagementSurfaceGuard` controllers):

  - **22** are `PlatformOwnerGuard`.

This is a correct property that must be preserved.

## 5. Architecture Decision

- **Host = context. Session = context, fixed at minting. Database membership = authority. RLS = independent barrier.**
- **Three session contexts:**

| Context | Host | Who can obtain it | Capabilities (unchanged RBAC) |
|---|---|---|---|
| `platform` | base host | `users.is_platform_owner = true` only | `PlatformOwnerGuard` routes |
| `organization:<orgId>` | `<org-label>.<base>` | A user with an `organization_memberships` row in that organization, **or** an active `academy_members` row in one of its academies | Existing management routes, **limited to that organization** |
| `academy:<academyId>` | academy subdomain or custom domain | Learners (and staff preview), as today | Existing learner routes for that academy |

- Each context is signed into the access token (`ctx: 'p'|'o'|'a'`, `cid: <orgId|academyId>`) and stored on the refresh row. **No role or permission is ever put in the token.**
- **Minimal enforcement: one check in each existing guard** (§11). No new authorization system.

## 6. Organization Host Model

**Label namespace [Rec]: one shared, single-level namespace for Organizations and Academies.** Four options were compared:

| Option | Edge TLS | Isolation | Change size | Verdict |
|---|---|---|---|---|
| **N1: shared `<label>.<base>` with one label registry** | Existing wildcard (Cloudflare edge `*.<base>` + Caddy DNS-01 wildcard) covers it unchanged | Host-only cookies and per-origin storage isolate every host; bearer tokens | Small | **Chosen** |
| N2: nested `<org>.manage.<base>` | Needs a second-level wildcard at the Cloudflare edge; Universal SSL covers only one level [X: verify], so Advanced Certificate Manager would be needed, plus a second Caddy wildcard | Same as N1 | Medium + recurring cost | Rejected (no security gain over N1, since isolation is per-origin either way) |
| N3: separate management apex (for example `atlasmanage.com`) | New zone and cert | Management hosts not same-site with tenant academy subdomains | Medium | Optional future hardening; not required because Atlas uses no parent-domain cookies and CSRF-relevant cookie auth |
| N4: path-based `atlas.com/o/<slug>` | none | Weaker: all organizations share one origin and one `localStorage` | Small | Rejected: it contradicts the hostname requirement and loses origin isolation |

**Representation [Rec]: ADAPT `subdomain_allocations` rather than creating a new table.** It already provides uniqueness, the regex, the reserved-list check, the availability service and a status lifecycle. The changes:
- `academy_id` becomes nullable.
- Add `organization_id` (UNIQUE, nullable).
- Add `CHECK (num_nonnulls(academy_id, organization_id) = 1)`.

The existing `subdomain` UNIQUE constraint then makes **one namespace across Organizations and Academies**. Alternatives considered:
- `organizations.management_label` UNIQUE: rejected, because cross-table uniqueness with academy labels would need triggers.
- A new `host_labels` table: rejected as a parallel system.

**Label rules** (reuse `SUBDOMAIN_REGEX`, 3–50 characters, plus these additions):
- Lowercase ASCII `a-z0-9-`, no leading or trailing hyphen, no `--` in positions 3–4. This blocks `xn--` punycode, so there are no homoglyph labels.
- **Reserved-list expansion (LB-RESERVED):** add `video` and `ssh` (existing infrastructure records [R]), plus `auth, login, signin, signup, register, account, accounts, billing, pay, payments, help, docs, blog, cdn, static, assets, media, files, email, smtp, imap, pop, mx, ns1, ns2, dev, staging, test, preview, demo, security, sso, id, identity, secure, internal, system, root, owner, manage, management, learn, academy, org, organization, www1-9`. Also add an impersonation list (`atlas*`, `admin*`, well-known brands) and a profanity list. The list stays in **one** backend constant, exposed to the frontend through the existing availability endpoint.
- **Arabic or other Unicode names:**
  - The display name stays free text.
  - The label is proposed from a transliteration where possible, otherwise from `org-<6 random>`.
  - The owner **chooses and confirms** the label at signup, with a live availability check. A label never has to be derived from the name.
- **Mutability:**
  - Immutable after creation (bookmarks, emails and trusted devices are host-bound).
  - A rename is a Platform Owner support action that keeps the old label as a **redirect-only alias for 90 days**, then releases it. This is a later feature, not a launch requirement.
- **Lifecycle:**
  - The label is released only when the Organization is purged, after a **cool-down** (default 90 days) to stop reuse phishing against old bookmarks.
  - Archived or suspended Organizations keep their label, and the host shows "This organization is not active".
- **Abuse:** per-user organization cap (plan v2); labels are rate-limited by the signup limiter.

## 10. Authentication Context Model

**Sign-in (one pipeline, `AuthService.signIn`, ADAPT):**
1. Resolve the context **server-side** from the request host through `HostContextService`, which extends `AcademySurfaceService`. The body's `surface`/`academyId` become **optional hints** that must agree with the host (existing `assertAcademyMatchesHost`, generalized). On local or preview hosts, the hint parameter is accepted only when `NODE_ENV !== 'production'`.
2. Run the existing steps in order: password → deleted, suspended or invited checks → **context admission** (the new step, replacing `resolveSurface`):
   - **platform:** `is_platform_owner` required; otherwise a generic refusal (§18).
   - **organization X:** an organization membership in X, or active academy staff in an academy of X. Otherwise:
     - A learner of an academy of X gets the learner redirect (§16).
     - Anyone else gets the generic "no access" (§16).
   - **academy X:** unchanged (student, staff preview, or open-policy join; the join becomes explicit in Phase 5).
3. TOTP, else email OTP under the **context's policy** (§12).
4. `issueSession(user, context)`, the single minter (unchanged location).

## 11. Session Model

| Element | Current [R] | Target |
|---|---|---|
| `refresh_tokens.surface` enum | `management`, `academy` | + `platform`, `organization`; `management` retired (test sessions are purged at reset) |
| `refresh_tokens` context id | `academy_id` | + `organization_id` |
| Access JWT | `{sub,sid}` | `{sub,sid,ctx,cid}` |
| `JwtAuthGuard` | sets `{userId,sessionId}` | also sets `{context, contextId}` |
| **Host binding** | none | Every authenticated request: host context must equal token context; mismatch → 401. One check in `JwtAuthGuard`, using the cached host resolver. |
| `ManagementSurfaceGuard` | refuses learner principals | also requires `ctx='o'` (organization) |
| `PlatformOwnerGuard` | `is_platform_owner` | also requires `ctx='p'` |
| `OrganizationMembershipGuard` / `AcademyScopeGuard` / `AcademyOrganizationScopeGuard` | derive org from the database | also require **resolved `organizationId` = token `cid`** (403) |
| Learner endpoints | host academy or `?academyId` | require `ctx='a'` and `cid` = host academy; `?academyId` dev-only |
| Refresh | rotates; host-agnostic | rotates; **refused unless the request host context = the row's context** |
| Password reset or change | revokes refresh rows and trusted devices | **+ denylist every live `sid`** (D3) |

- **The 8 guard-less management controllers** each get a per-route decision in Phase 2:
  - `instructor` and `search`: filter by `cid`.
  - `course-order-payments`: resolve the order's organization, then compare.
  - `blog-posts`: resolve the academy's organization, then compare.
  - `payment-methods`, `subdomain-availability`, `infrastructure`: catalogue or read-only, so `ctx='o'` or `'p'` is enough.
  - `platform/organizations`: `ctx='p'`.
- **Account endpoints** (`/users/me*`, password, 2FA, sessions, trusted devices) accept any context. A user manages their own account from any host.
- **Cookies:** stay **host-only**; nothing is ever set on `.<base>`. A parent-domain cookie would be sent to tenant academy hosts too.
- **Tokens:** stay in per-origin `localStorage`. Different organizations are different origins, so session reuse across them is impossible in the browser and refused by host binding at the API.

## 12. OTP / MFA Model

- **Reuse:** `EmailOtpService`, `auth_email_challenges`, `AuthChallengeCipher`, the budgets, resend and attempt limits, `TrustedDeviceService`, `TwoFactorService`.
- **Context binding [R: already partially true]:**
  - The code hash is salted with the challenge **row id**, and verify reads that row only, so a code **cannot** verify another challenge.
  - The surface and academy come from the row.
  - **Adapt:** add `organization_id` to `auth_email_challenges`. The context `(surface, academy_id|organization_id)` is written at issue and re-admitted at completion.
- **Invariants that follow:**
  - A code for Organization A cannot authenticate into B (different row, and completion re-admits context A only).
  - An academy code can never mint an organization session.
  - A platform code can never mint an organization session.
  - Additionally, **completion must happen on a host whose context equals the challenge context**, else a generic failure.
- **Supersede scope:** changes from `(user, surface)` to `(user, surface, context_id)`. At most 3 live challenges per user, oldest superseded. This fixes the multi-tab and multi-academy "expired code" UX (plan v2 F1) while keeping the guessing budget bounded.
- **TOTP challenge:** store the context (plan v2 F2).
- **Trusted devices:**
  - Add `organization_id` and `academy_id`; match on (user, surface, context id).
  - The cookie stays host-only, so a device trusted for org A is not trusted for org B (cookie scope) and cannot be (row scope).
- **Organization OTP policy (new setting):**
  - Column: `organizations.management_otp_policy` (enum `off | new_device | always`, **NULL = platform default**).
  - **Default [R-derived]:** NULL. This inherits `FLAG_AUTH_EMAIL_OTP_MODE_MANAGEMENT`, which is **`new_device` in production today**, so every Organization starts with "email code on new devices" = **ON**. This follows the existing precedent that a null tenant security setting means platform default (`academies.content_protection`, `video_security_tier`).
  - UI "Require OTP for management sign-in": **ON** = `new_device` (default), **OFF** = `off`. An advanced "every sign-in" = `always`.
  - **Authority:** Client Owner only. The check is `organizations.owner_user_id = user` **and** the `owner` membership role, mirroring existing owner-only settings such as registration policy (D8). Managers and Instructors hold no permission to change it; none of `ORGANIZATION_MANAGER_PERMISSIONS` covers security settings [R].
  - **Platform floor:** a platform setting `min_management_otp_policy` (default `off`, so the owner's choice is honoured). Atlas can raise the floor later without code. **Owner decision** (§37).
  - Changing the setting writes an audit entry and emails the owner.
- **Platform context:** keeps using the management env flag. **Launch gate:** every Platform Owner account has **TOTP enabled** (operational requirement; no code).

## 13. Password Reset Model

- **One backend service** (`requestPasswordReset` / `isPasswordResetTokenValid` / `confirmPasswordReset`, ADAPT) plus context-aware links.
- **Request:**
  - The context is derived from the **request host** (never the body).
  - The **response is identical in every case** (existing behaviour).
  - The token row stores `context_surface` + `organization_id`/`academy_id` (ADAPT `password_reset_tokens`).
  - Email:
    - **The user has access to that context** (org membership, academy student or staff, Platform Owner): reset link on **that context's canonical host from the database**. Organization → `https://<org-label>.<base>/auth/reset-password?token=…`. Academy → `https://<academy-host>/reset-password?token=…`. Platform → base `/auth/reset-password`.
    - **The account exists but has no access to that context:** an email saying "you asked to reset your password at *acme.<base>*, but this account doesn't manage that organization. If you learn at an academy, use its website." There is **no link and no list of relationships**. The requester sees nothing different. The mailbox owner learns only their own facts.
    - **No account:** no email (existing).
- **Validate / confirm:** the token is accepted **only on a host whose context equals the token's context**, else the generic `invalid token`. This stops a token being used cross-context and keeps the flow on the right host.
- Confirm changes the password, revokes all refresh rows, trusted devices **and live `sid`s** (D3), marks the email verified (the link proves the mailbox), and **mints no session**. The user then signs in on the same host, and normal admission applies. **A reset token never grants tenant access.**
- **Link host building** stays in `LinkBuilderService`, from the **database** (new `branding:'organization'` resolves the org label host). The request `Host` header is **never** used to build links, which prevents host-header reset poisoning.

## 14. Signup Model

- **Where:** base host `/auth/register` (the existing route and the existing one-page signup). Organization hosts have **no** signup route: `AppRouter` does not mount it, and the backend refuses `POST /auth/register` unless the host context is `platform` or an academy.
- **Same pipeline**, with the existing organization-creation port `SignupOrganizationPort` (`createInTransaction`: org, owner membership, subscription, trial, audit, outbox). Adapted to:
  - Allocate the **organization label** in the same transaction (the label is chosen and validated on the form).
  - Adopt plan v2's **mailbox-first, non-enumerating** start/verify (the code proves the mailbox; an existing account also needs its password) and the eligibility rules: learners, instructors, managers and existing owners are eligible; **Platform Owners are excluded** by guard and trigger; a per-user owned-organization cap.
- **Completion:**
  - The platform-host session **cannot** be used on the new organization host (different origin, context `platform` is not admitted for customers).
  - Completion therefore mints a **single-use hand-off code** (256-bit, hashed at rest, 60 s, audience = the new org id + org host, created **only** by signup completion for the organization just created) and redirects to `https://<org-label>.<base>/auth/continue#code=…`.
  - The org host SPA exchanges it once (`POST /auth/handoff/exchange`, host-bound, atomic consume). This runs org admission (the user is the owner) and **the org OTP policy**, which the signup mailbox code satisfies (the same email factor, minted less than 60 s earlier).
  - This avoids a second password and a second email code right after signup, which is valuable given KI-EMAIL-1.
- **Why this narrow hand-off is acceptable** when plan v1/v2 deferred general SSO: both ends are **Atlas-owned origins**, there is exactly **one** issuing path (signup completion), and the audience is a host created milliseconds earlier by the same transaction. No tenant-controlled origin is involved. **Fallback:** if the hand-off fails or expires, the org host shows "Your organization is ready — sign in" with the email prefilled.

## 15. Invitation Model

Reuse `AcademiesService.addManager/addInstructor/createStudent` + `AccountSetupService` (the reset-token-based setup link). Adapt:

- **D2 fix (launch blocker):**
  - A new person is created with `status='invited'` and an **unusable password hash**. The `password` field in the staff-add DTOs is ignored (with a deprecation warning).
  - Sign-in as `invited` gets a generic 401.
  - The setup link (existing token, 3-day TTL) sets the password, activates the account, and marks the email verified.
- **Setup link host:**
  - Staff (`academy.member.invited`) → the **organization host** `/auth/reset-password?token&setup=1` (new `branding:'organization'`).
  - Learners (`academy.learner.invited`) → the academy host `/reset-password?token&setup=1` (unchanged).
- **Existing global identity added as staff:** attached (existing behaviour), and **now notified** by email with a link to the org host sign-in. No new account and no password change.
- **First login:** the org host sign-in with password plus the org OTP policy.
- **Expired link:** "forgot password" on the org host issues a fresh one (the account exists).
- **Removed membership:** org admission fails, and the account stays.
- **Multi-role users:** unchanged; relationships add up.
- Explicit accept-invite for existing identities: optional later (plan v2 decision 6).

## 16. Organization Dashboard Routing

- **One SPA, one dashboard, one component tree.** `AppRouter` gains mode `organization-management` for org hosts. It mounts:
  - The existing `/auth/sign-in`, `/auth/forgot-password`, `/auth/reset-password`, `/auth/verify-email`, `/auth/continue` (new).
  - The existing **`/dashboard/*` tree minus Platform-Owner routes**.
  - It does **not** mount `/auth/register`, marketing pages or `/dashboard/platform*`.
- **Active organization:**
  - `PlatformProvider.activeOrganizationId` is **set from the host context** and not user-switchable.
  - `OrganizationSwitcher` becomes a list of **links to the other organization hosts** from `/users/me` memberships (each opens that host's sign-in).
  - Pages that read `activeOrganizationId` keep working unchanged.
- **The learner on an org host (§10 case):**
  - After a **correct password only** (never before), a learner of an academy of *this* organization sees: "Your account is used as a learner at *Acme Academy*. Learners sign in on the academy website. [Go to Acme Academy]".
  - This reveals only the person's **own** relationship with the organization named by the host. It is shown after password proof, before OTP, and **no code is emailed**.
- **Unrelated user:** after a correct password, "This account doesn't have access to this organization." No other information, the **same message** a learner of another organization gets, and no code is emailed.
  - Before password proof, every failure is the existing generic `invalidCredentials`. No membership oracle exists without the account's password.

## 17. Academy Routing

Unchanged, plus plan v2's role-aware post-login card: staff of that academy see "Open management dashboard" → **their organization host** `/auth/sign-in?email_hint=…&next=/dashboard/academy/<id>`.

## 18. Platform Owner Routing

- **Base host** `/auth/sign-in`, `/auth/forgot-password`, `/auth/reset-password`, `/dashboard/platform*` (existing routes). Context `platform`.
- **Admission:** Platform Owners only. A customer who signs in there with a correct password sees "Customer accounts sign in at your organization's address" + **[Find my organization]**.
- **Find my organization (new, small):**
  - `POST /auth/find-organizations {email}` always returns 202 (rate-limited).
  - The **email** lists the org hosts the account can manage, or says there are none.
  - Pattern: an email-channel workspace finder [X: common SaaS practice; verify].
- **Audit before restricting** (Phase 4): every `/auth/sign-in` reference, emails with `/dashboard` links (`communication-catalog.ts`: `/dashboard`, `/dashboard/support/:id`, `TENANT_BILLING_PATH`, profile paths) → retargeted to `branding:'organization'`; the deploy and verify scripts; the Playwright journeys.
- A Platform Owner who is also a learner uses the academy host as a learner. Platform Owners never hold customer organization sessions (the trigger excludes ownership; admission requires membership).

## 19. Account Center

## 22. DNS

- **Reuse:** the proxied wildcard `*.<base>` + apex. **No per-organization DNS record, ever.** A new organization is live the moment its label row commits.
- **Keep grey-cloud or explicit records** (`ssh`, `video` Worker route) and put them on the reserved list (LB-RESERVED).
- **LB-DOMAIN:** move to an Atlas-owned registrable domain before launch. After launch, every org host, academy subdomain, email link, trusted device and bookmark is bound to the domain, so changing it later means a re-migration of every tenant.
- Also check whether the chosen apex is on the Public Suffix List [X: verify]. A normal registrable domain is **not**, which means all `*.<base>` hosts are **same-site**. That is acceptable: Atlas uses bearer tokens, not ambient cookies, and its cookies are host-only and read only at sign-in.

## 23. TLS / SSL

- **Reuse:** the Cloudflare edge certificate for `<base>` and `*.<base>` (Universal SSL covers the apex plus one wildcard level [X: verify]), and the Caddy origin wildcard via DNS-01 (existing `tls { dns cloudflare }`).
- Custom domains stay on Cloudflare for SaaS (existing).
- HSTS: `includeSubDomains` on the platform block is already present [R], and it covers org hosts.
- No change needed for N1.

## 24. Frontend Host Resolution ("middleware")

There is no server middleware. The SPA's `resolvePublicWebsiteContext` is **ADAPTED**:
- Base or `www` → `platform`.
- Local or IP → `platform` (dev, with preview params).
- Single label under the base → **call `GET /api/v1/public/host-context`** (new, public, cached by the SPA for the page lifetime). The answer is `{kind:'organization', org:{name, logoUrl}} | {kind:'academy', …existing website data} | {kind:'unknown'}`.
- Other hosts → academy (custom domain; the existing path).
- `kind='unknown'` renders a neutral "This address isn't in use" page. **No redirect**, so unknown or typo-squatted labels don't become redirectors.
- Exposing the organization name and logo on its own management host is not an enumeration issue: the host is public, like an academy site.

## 25. Backend Host Resolution

- **`HostContextService` (ADAPT `AcademySurfaceService`):** `resolve(hostname) → {kind, id}` through the new SECURITY DEFINER `resolve_host_context(host,label)`, which extends `resolve_public_hostname` with an org branch.
- **Caching:** an in-process LRU (60 s TTL). A future Redis pub/sub invalidation on label or domain changes is non-blocking at launch scale.
- **Host trust (LB-HOST):**
  - Express uses `trust proxy = loopback, linklocal, uniquelocal` [R], so `request.hostname` honours `X-Forwarded-Host` **from Caddy**.
  - Caddy trusts Cloudflare ranges (`trusted_proxies`) [R]. Whether a **client-supplied** `X-Forwarded-Host` survives Cloudflare → Caddy is **unverified** [X: verify].
  - **Fix regardless:** Caddy `reverse_proxy` sets `header_up X-Forwarded-Host {host}` (the actual request Host that Cloudflare routed on). The backend resolves the context from that value only.
  - Add a startup assertion and an e2e probe with a spoofed header.
  - **Impact if spoofed:** context confusion only, never authorization. Admission, membership, guards and RLS still decide. The fix makes it deterministic.
- Links are never built from the request host (§13).

## 39. Definition of Done: answers to the 28 questions

1. **New Client Owner hostname:** chosen on `/auth/register` (with an availability check), allocated in the signup transaction (`subdomain_allocations.organization_id`), live immediately via wildcard DNS and TLS.
2. **Existing organizations:** test organizations get backfilled `org-<6>` labels; after the reset, every organization gets one at creation.
3. **The same user across organizations:** separate sign-in per org host; each session is bound to that organization; permissions come from that organization's membership.
4. **Manager:** org host `/auth/sign-in` → password → org OTP policy → org session.
5. **Instructor:** same as the Manager; instructor permissions unchanged.
6. **Learner:** the academy host `/sign-in` (unchanged).
7. **A learner on an org login:** after a correct password, an own-relationship message with an academy link; no session, no code emailed.
8. **An unrelated user:** generic failure before the password; after the password, the generic "no access to this organization"; no code, no information.
9. **OTP:** the existing email OTP, bound to the challenge row and context, completed only on the matching host.
10. **Who controls organization OTP:** the Client Owner only (`organizations.management_otp_policy`; NULL = platform default = `new_device` today).
11. **Forgot password:** the host-derived context, identical response, email link to that context's database canonical host.
12. **Context preserved on reset:** the token row stores the context; validate and confirm only on the same context host; no session minted.
13. **TOTP:** unchanged factor; its challenge stores the context.
14. **Trusted devices:** a host-only cookie plus a row bound to (user, surface, context id).
15. **Session scope:** `ctx` + `cid` signed in the JWT and stored on the refresh row; host binding on every request; tenant-guard equality.
16. **RLS unchanged:** no policy changes except additive ones and the plan v2 tightenings.
17. **Dashboard unchanged:** the same `/dashboard/*` tree mounted on org hosts; the active organization comes from the host.
18. **RBAC unchanged:** no role or permission changes; the guards only add a narrowing check.
19. **Academy custom domains unchanged:** the same resolver path; they never resolve to an organization.
20. **Platform Owner unchanged:** the base host, the same routes and guards, plus a context requirement.
21. **Old `/dashboard`:** Platform Owner routes stay on the base host; others show the compatibility landing with "Find my organization".
22. **100,000+ organizations:** the wildcard; an indexed label lookup; a cached resolver; no per-tenant infrastructure.
23. **Hostname spoofing:** the host is context only; Caddy overwrites `X-Forwarded-Host`; links come from the database; admission, guards and RLS authorize.
24. **Cross-tenant cache leakage:** `no-store` on authenticated routes; `Vary: Host` + `no-store` on host-dependent public responses; `/api` not cached.
25. **Safe production migration:** additive schema, test-data verification, controlled reset, clean launch (§34, §39).
26. **Rollback:** §35.
27. **Exact code that changes:** §FINAL-B/C.
28. **Exact code that does not change:** §FINAL-A.

**Production data reset procedure (Option C, recommended).** This is **hybrid: keep the platform, delete the tenants.**

Chosen over the alternatives:
- **A (migrate test data):** preserves nothing of value and carries test artefacts into real production.
- **B (full wipe):** also destroys platform configuration (plans, pricing, trial policy, commission, provider configuration) that must then be re-entered by hand, which is error-prone.

| Preserve | Delete | Migrate | Recreate |
|---|---|---|---|
| `schema_meta`, `_prisma_migrations`, `plans`, `add_ons`, `trial_policy`, `platform_settings`, `platform_domain_configuration`, `atlas_commission_config`, `plan_commission_settings`, `atlas_subscription_payment_provider_config`, `payment_methods` (empty; to be configured), platform-scope `access_policies`, **Platform Owner `users` rows** (and their TOTP) | Every organization, academy, membership, learner, course, content, enrollment, progress, quiz, assignment, certificate, order, payment, invoice, payout, ledger, subscription, add-on, usage, provisioning, website, domain, subdomain, live session, notification, outbox, delivery, digest, support case, audit entries tied to tenants, refresh tokens, challenges, trusted and student devices, trial redemptions (test mailboxes; decision), suppressions (test addresses), non-Platform-Owner users | Nothing | Organization labels on first real signup; Prometheus series (optional volume reset) |

**Procedure:**
1. Written runbook plus sign-off.
2. **Maintenance window:** Caddy serves a maintenance page for `/api/*` (except `/health`); stop backend workers; drain BullMQ.
3. **Backups:** `pg_dump -Fc` to the existing `atlas-backups-production` R2 bucket, verified by a restore into a scratch database. Also a manifest of R2 keys and Stream video ids.
4. **Dependency analysis:** generated from `pg_constraint` (the FK graph) and checked against `ON DELETE` rules (Cascade, SetNull, Restrict), so the order is computed, not guessed.
5. **External resources first:**
   - Delete Cloudflare custom hostnames for test academies through the existing `DomainProviderRelease` / `deleteCustomHostname`, confirmed gone.
   - Delete Cloudflare Stream videos by the manifest.
   - Delete R2 tenant objects by prefix (keep the platform prefixes).
   - Worker KV `GATE_DENYLIST`: clear test entries.
6. **Database:** one transaction as the owner role (not `atlas_app`, because RLS would hide rows):
   - `TRUNCATE … CASCADE` on the tenant roots (`organizations`, and tenant tables not reachable by cascade).
   - `DELETE FROM users WHERE NOT is_platform_owner`.
   - Assert the preserved tables' row counts are unchanged.
7. **Redis:** flush the revocation, rate-limit, relationship-cache and BullMQ keys (or `FLUSHDB` after the drain).
8. **Email:** nothing is stored at Brevo; review test contacts, if any.
9. **Metrics and logs:** optionally reset the Prometheus volume (test contamination); Sentry is unchanged.
10. **Verification SQL:** zero rows in every tenant table; platform configuration intact; Platform Owner can sign in with TOTP; `/public/plans` is correct.
11. **Recovery:** restore from the dump; R2 deletions are irreversible, which is accepted for test media, or an optional copy to the backup bucket is made first.

### E. SECURITY IMPACT

**Strictly stronger:**
- Every token is confined to one context and one host.
- Academy tokens lose management reach (D1).
- Organization tokens lose cross-organization reach, even for multi-organization users.
- Platform Owner tokens only work on the base host.
- Password changes kill sessions immediately (D3).
- No account has a password set by someone else (D2).
- Signup stops revealing which emails have accounts.
- Reset links can't be poisoned by the Host header and can't be used cross-context.
- OTP stays row-bound and becomes host-matched.
- CSP and RLS tightening close the defence-in-depth gaps.

**No weakening:** authorization remains database-derived; hostnames never grant anything.

### F. MIGRATION IMPACT

**On current (test) production users:**
- Sessions end at the cut-over or reset.
- Customer dashboards move to org hosts.
- All tenant data is deleted in the controlled reset.
- Platform Owners and platform configuration are kept.

**On real customers after launch:** none of this; they start on the final architecture.

## FINAL QUESTION

> *Can we take the current Atlas production system, make the minimum necessary architectural changes for Organization hostnames and context-bound authentication, safely clean/reset the current fake production data, and then use the resulting system as the real commercial Atlas production platform?*

**YES, conditionally.**
- **Why:**
  - The hard parts already exist and are sound: one global identity; relationship-based RBAC; per-request, database-derived tenant guards; forced RLS with a non-bypass application role; a wildcard DNS and TLS topology; a hostname resolver; custom domains; a database-sourced link builder; a hardened OTP and TOTP core.
  - Organization hostnames fit as **one more resolved context** on the same resolver and guards.
  - The test-data reset removes every migration and backfill problem.
- **Required changes:** §FINAL-B (adapt) and §FINAL-C (new). No rewrite of authentication, RBAC, RLS, the dashboard, academies, billing or communications.
- **Conditions, i.e. launch blockers that must be closed first:**
  - **LB-DOMAIN** (an Atlas-owned domain).
  - **D1, D2, D3** (session and credential security).
  - **LB-HOST, LB-RESERVED** (small infrastructure fixes).
  - **LB-CSP, LB-RLS** (defence in depth).
  - **LB-PAY** (a payment path).
  - **LB-EMAIL** (measured email reliability for OTP, reset and invites).
  - **LB-BACKUP** (a rehearsed restore).
  - **LB-PO-2FA** (TOTP on Platform Owner accounts).
- None of these is hidden behind a flag, and all are in Phases 1–6 and the Production Launch Gate. Until the gate is green, the system is **not** production-ready.
